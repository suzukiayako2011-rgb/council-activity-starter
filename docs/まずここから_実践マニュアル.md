# まずここから：実践マニュアル

**全部を一度に完成させる必要はありません。今いる段階から進めばよいです。**
初めてなら、下のステップ1から順に進めてください。途中までできている方は、完了条件を確認し、その次から始めてください。今日は1件を整理するだけでも構いません。

各ステップは「やること → AIにそのまま貼る文 → 自分で確認すること → ここまでできたら次へ」の順です。チェックを付けながら使ってください。三神本人がその場にいなくても進められる手順です。

ChatGPT・Claudeなど、普段使うAIで進められます。特定のモデルは必須ではありません。プロンプト内の `［…］` は自分の情報に置き換えます。分からない場合は「分からない」と伝えます。

| 今できていること | 始める場所 |
|---|---|
| まだ会議録を選んでいない | [ステップ1](#step-1) |
| 必要な質問と答弁を手元に保存した | [ステップ2](#step-2) |
| AIが1件整理した | [ステップ3](#step-3) |
| 原文と見比べた | [ステップ4](#step-4) |
| starter-0.1で1件保存した | [ステップ5](#step-5) |
| 同じ形で3件程度保存した | [ステップ6](#step-6) |
| 仮ページを公開し、翌日も更新できた | [ステップ7](#step-7) |
| 自分の記録を公開している | [ステップ8](#step-8) |

READMEは[入口](../README.md)、[全体像](全体像.md)は地図です。このファイルは作業中のナビとして使います。

先に[安全と表現のルール](../README.md#はじめる前に必ず確認すること)を読みます。この手順では、会議録検索サイトへの自動アクセス・自動取得は行いません。人がブラウザで確認します。個人情報・市民からの相談・非公開資料・秘密情報は、AIにも公開Q&Aにも入れません。

<a id="step-1"></a>
## ステップ1：自分の議会の会議録を1件開く

### 1. やること

1. ブラウザで、自分の議会の公式サイトを開きます。会議録検索への案内を探します。
2. 利用規約を読みます。扱いが分からなければ議会事務局に確認します。コピー・保存・AIへの入力は、自治体の利用条件に従います。
3. 日付や自分の名前で探し、公開済みの会議録を1件開きます。
4. 自分の質問・提案が始まる位置と、それに対応する答弁を探します。まず1つの論点を選びます。
5. 確認できたURLを手元に控えます。発言ごとのリンクがある場合は、対象の質問が始まるリンクを開き直し、位置を確認します。

URLはページの場所を示すアドレスです。控えただけでは内容を確認したことになりません。発言位置のURLを確認できなければ、推測で作らず、そのことをメモします。

### 2. AIにそのまま貼る文

```text
自分の議会の公開会議録から、質問と答弁を1件選びます。
会議録検索サイトへ自動アクセス・自動取得しないでください。
私がブラウザで操作します。次に確認することを1つだけ教えてください。
議会名：［議会名］
今の状態：［公式サイトを開いた／検索で止まった、など］
```

### 3. 自分で確認すること

- [ ] 公式の会議録で、利用条件を確認した。
- [ ] 自分の発言であることと、日付・会議名を確認した。
- [ ] 選んだ質問・提案と、対応する答弁の位置が分かった。
- [ ] URLを開いて位置を確認した。分からなければ、未確認と記録した。

### 4. ここまでできたら次へ

**1つの論点について、質問・提案と答弁を自分で読めたら、ステップ2へ進みます。** 利用条件が不明なら、コピーやAI入力の前に確認します。

<a id="step-2"></a>
## ステップ2：必要な範囲をAIに渡して1件整理する

### 1. やること

1. 選んだ質問・提案と答弁を、意味が分かる必要範囲だけコピーします。再質問が関係する場合は、その答弁まで含めます。
2. 手元の作業フォルダにテキストファイルを作ります。1行目に確認した会議録URLを貼ります。未確認なら「出典URL未確認」と書きます。
3. 日付・会議名・発言者も控えます。ファイル名は `2026-06-12_本会議_一般質問.txt` のようにします。
4. 個人情報や非公開情報が混ざっていないか確認して、AIに添付します。添付できなければ、必要範囲だけ貼ります。
5. 下の文を貼り、まず1件だけ整理させます。

コピーした原文は手元に残します。**原文・全文・PDF・ZIP・大量の本文断片は、公開・非公開を問わずGitHubに置きません。** 保存先は自分のパソコンなどにします。詳しくは[議事録の集め方と保存](議事録の集め方と保存.md)を参照してください。

### 2. AIにそのまま貼る文

```text
添付した必要範囲から、1つの論点だけ整理してください。
日付、会議名、論点、課題、質問・提案、対応する答弁の要旨、出典URLを示してください。
資料にない情報は推測せず、不明としてください。URLも生成しないでください。
会議録サイトへ自動アクセスしないでください。
複数論点がある場合は、分ける候補を示し、まず1件だけ整理してください。
私の名前：［名前］／今回の論点：［論点］
```

### 3. 自分で確認すること

- [ ] 質問だけでなく、対応する答弁も渡した。
- [ ] 個人情報・非公開情報・秘密情報を渡していない。
- [ ] 原文はGitHubのフォルダに入れていない。
- [ ] AIの結果は1つの論点になっている。

### 4. ここまでできたら次へ

**1件の整理案ができたら、ステップ3へ進みます。** AIが返しただけでは、確認済み・公開可能にはなりません。

<a id="step-3"></a>
## ステップ3：AIの整理結果を原文と見比べる

### 1. やること

1. 元の会議録とAIの整理案を並べて開きます。
2. 下の確認項目を1つずつ読み比べます。答弁が質問のどの部分に応じたかも見ます。
3. 誤りは原文を根拠に直します。確認できない情報は推測で補いません。
4. 出典URLを自分で開き、対象の質問の位置を確認します。答弁も読めるか確認します。

AIに比較を手伝わせても、最後はデータを公開する議員本人が原資料を読んで確認します。URLの位置確認と、内容の照合は別々に行います。

### 2. AIにそのまま貼る文

```text
先ほど渡した原文と整理案を比べ、日付、会議名、論点、質問・提案、答弁要旨の
食い違いと、原文に根拠がない記述を挙げてください。
分からないことは埋めず、確認が必要な点として示してください。
URLは私がブラウザで確認します。自動アクセスしないでください。
確認済みと確定するのは私です。
```

### 3. 自分で確認すること

- [ ] 日付・会議名が原資料と一致している。
- [ ] 論点と、質問・提案の対象範囲が変わっていない。
- [ ] 答弁要旨に、原文にない約束や実施の断定がない。
- [ ] 出典URLが別の日・別の会議・別の発言を指していない。
- [ ] 確認できない情報を推測で埋めていない。

### 4. ここまでできたら次へ

**原文と比較して直し、残る不明点を特定できたら、ステップ4へ進みます。** 不明点が残る記録は、公開用と分けて作業用に保存します。

<a id="step-4"></a>
## ステップ4：starter-0.1の形にする

### 1. やること

1. [データの形（暫定版）](データの形_暫定版.md)、[見本JSON](../examples/starter-0.1.json)、[JSON Schema](../examples/starter-0.1.schema.json)を開きます。
2. 各ファイルを保存してAIに添付します。難しければ、ファイル本文をコピーし、ファイル名を付けて別々に貼ります。リンクだけで読めたと思い込まず、3資料の内容を受け取れたかAIに確認します。
3. 自分用の `dataset.slug` を決めます。半角小文字・数字・ハイフンで、例えば `your-slug` とします。一度決めたら変更しません。
4. ステップ3で直した整理案を渡し、下の文で変換を頼みます。既存データがある場合は、そのファイルも渡します。
5. 返されたJSONを、自分用の `activity.json` などの名前で手元に保存します。見本の架空データは混ぜません。

JSONは項目名と値で記録する形式です。JSON Schemaは、その形式を検査するためのルールです。どちらも事実の正しさを保証しません。

1件は1つの論点です。1つの求めと対応する答弁を基本単位にします。予算要望では、要望書上の1項目を1件にします。

`id` は記録を指し続ける恒久IDです。`your-slug-000001` のように6桁の通し番号を付けます。並べ替えや修正で変えず、削除した番号も再利用しません。

`result_level` は当時の答弁・回答に基づく対応状況です。**迷えば `null`（値が未確定である印）にします。** 値を入れる場合は、[新基準の6区分と判定原則](データの形_暫定版.md#対応状況の6区分)を読みます。AIは候補提示まで。確定はデータを公開する議員本人が行います。

三神たかしの公開DB／サイトは新しい「実施済」基準への移行監査中で、既存値・表示には旧基準が残っています。新規データの判定基準として旧表示をコピーしません。

### 2. AIにそのまま貼る文

```text
添付した暫定仕様・見本JSON・JSON Schemaを読めたか、まず確認してください。
読めたら、私が照合した整理案をstarter-0.1のJSONにしてください。
schema_versionはファイル全体に1つ。recordsに記録を入れ、見本の架空データは除いてください。
slug：［決めたslug］／新規ID：［slug-000001など、未使用の番号］
既存のslugとIDは変えず、独自項目を足さないでください。
不明はnull。source_urlは私が確認したURLだけ。未確認ならnull。
result_levelは今回はnull。tagsは共通15分類、自由タグはlocal_tagsに分けてください。
JSON Schemaで形式を検査できるなら実行し、できなければ未実施と伝えてください。
IDの重複・slugとの一致は別途確認してください。
```

### 3. 自分で確認すること

- [ ] ファイル全体の `schema_version` は `starter-0.1` で、カードに繰り返していない。
- [ ] `dataset.slug` が決めた値で、各IDの接頭辞と一致している。IDは重複していない。
- [ ] 1件1論点。予算要望は要望書上の1項目1件になっている。
- [ ] 必須の項目名が揃い、独自項目を追加していない。
- [ ] 不明は `null`。空文字や「未判定」を値にしていない。
- [ ] `tags` は共通15分類。自由タグは `local_tags`。付けないと決めた自由タグは空配列 `[]`、未確認は `null`。
- [ ] `result_level` は `null`、または本人が確定した6区分の値。後年の情報を判定に使っていない。
- [ ] `source_url` は自分が確認したURL、または `null`。AIの推測URLではない。
- [ ] 保存したJSONが開ける。形式検査が実行されたか、未実施なのか分かっている。

### 4. ここまでできたら次へ

**1件を同じ項目名・値の形で保存できたら、ステップ5へ進みます。** 形式のエラーがあれば先に直します。Schema検査だけではIDの重複・slugとの一致・事実の正しさは確かめられません。

<a id="step-5"></a>
## ステップ5：まず3件程度作る

### 1. やること

1. ステップ1〜4を繰り返し、別の論点を2件程度整理します。1件だけで公開へ進まず、同じ形で作れるか試します。
2. 同じJSONの `records` に追加します。slugを維持し、新しい未使用IDを付けます。
3. 3件程度を見比べます。項目名や分類の表記が揃っているか確認します。
4. JSON Schemaによる形式検査を、まとめたファイルに対して行います。実行方法が分からなければ、AIに1つずつ案内させます。

### 2. AIにそのまま貼る文

```text
このstarter-0.1のファイルに、私が原文照合した次の1件を追加してください。
既存の記録・slug・IDを変えず、新規IDは［未使用ID］にしてください。
項目名・null・共通分類を揃え、JSON Schemaで形式を検査してください。
IDの重複とslugの接頭辞も別途確認してください。実行できない検査は明示してください。
原文照合を済ませた新しい整理案：［整理案］
```

### 3. 自分で確認すること

- [ ] どの記録も原文と照合した。既存の記録が勝手に書き換わっていない。
- [ ] 3件程度が同じファイル・同じ形式にまとまっている。
- [ ] IDの重複・再利用がなく、slugが揃っている。
- [ ] JSONの形式検査を実行し、エラーを直した。
- [ ] 原文や大量断片をデータファイルに混ぜていない。

### 4. ここまでできたら次へ

**同じ手順で3件程度保存し、形式が安定したら、ステップ6へ進みます。** ここで止めて、手元で記録を増やしても構いません。

<a id="step-6"></a>
## ステップ6：公開テストをする

### 1. やること

1. [公開テスト](公開テスト.md)を開きます。この段階では、実際の議会活動データを載せず、仮ページ1枚を公開します。
2. 自分用のGitHubリポジトリを用意します。リポジトリはファイルをまとめて保存する場所です。
3. このスターターの `starter/` の中身だけを使います。`wrangler.jsonc` を一番上、`index.html` を `public` フォルダ内に置きます。
4. 手順書に沿い、自分用の名前に直し、Cloudflare等で公開します。料金・条件は開始時に公式情報で確認します。
5. 発行された仮URLを開きます。翌日、文章を1か所直し、再公開して反映を確認します。

Cloudflare等は、ページをインターネットに公開するサービスです。画面名が違うときは、現在の画面と手順書をAIに渡し、次の操作だけ聞きます。スクリーンショットの秘密情報・個人情報は隠します。

**独自ドメインの接続・既存HPへの統合は、HP業者に確認してから進めます。** まず仮URLで試します。

### 2. AIにそのまま貼る文

```text
添付した「公開テスト」の手順で、仮ページ1枚を公開して更新する練習をします。
手順書と今の画面を見て、次に私がする操作を1つだけ教えてください。
画面で確認できないボタン名や設定は推測しないでください。
実データや会議録原文は載せません。独自ドメインや既存HPは変更しません。
今の状態：［初回公開の途中／翌日の更新、など］
```

### 3. 自分で確認すること

- [ ] 仮URLを開くと、テストページが見える。
- [ ] 原文・個人情報・パスワード・APIキー等を公開していない。
- [ ] 翌日、自分で文章を1か所直して再公開し、反映を確認した。
- [ ] テスト用の検索エンジン除外指定 `noindex` を、この段階では維持している。

### 4. ここまでできたら次へ

**翌日も自分で更新できれば公開テストは合格です。ステップ7へ進みます。** 初日に公開できただけでは、まだこの段階は終わりません。

<a id="step-7"></a>
## ステップ7：自分のデータを検索ページに載せる

### 1. やること

**現時点では、このスターターに検索画面の雛形はありません。** `starter/public/index.html` は公開テスト用です。JSONを置くだけで検索ページになるわけではありません。

1. まだ検索ページがない方は、確認済みの3件程度のJSONと暫定仕様をAIに渡します。まず、手元で試せる最小の検索ページの作成を頼みます。
2. 題名・質問・答弁・出典が読めるか試します。キーワードで探し、0件の場合も確かめます。難しければ手元の整理に戻り、[Discussions](https://github.com/threegod1225/council-activity-starter/discussions)で相談します。
3. 既に検索ページがある方は、今のページが受け取れる形式を確認します。starter-0.1をそのまま読めない場合は、元データを残し、変換方法を確認してから追加します。
4. 公開予定の各記録を、もう一度原資料と照合します。URLが `null` の記録は、原資料の所在と内容を人が確認できるまで公開対象から外します。
5. 仮URLで表示を確認してから公開します。本番で検索エンジンに載せる場合は、公開テスト用の `noindex` を外します。

同一発言ブロックから分けた記録だけがURLを共有できます。別ブロックのURLを会議単位のURLで一括上書きしません。本人の原文照合を経た記録だけに確認済み表示を付けます。AIの検査だけで確認済みにしません。第三者の検証を経ていない場合は、その旨をサイトに明記します。

### 2. AIにそのまま貼る文

```text
確認済みのstarter-0.1 JSONと暫定仕様を渡します。
まず手元で試す、キーワード検索付きの最小ページを作ってください。
題名・質問提案・答弁要旨・確認した出典リンクを表示してください。
nullを推測で補わず、ID・判定・データ形式を変えないでください。
原文の取り込みや会議録サイトへの自動アクセスはしないでください。
自動で公開せず、試し方と次に私がする操作を1つずつ教えてください。
既存ページがある場合は、まず読めるデータ形式と追加方法を確認してください。
```

### 3. 自分で確認すること

- [ ] 検索語で期待した記録が見つかり、0件でも画面が崩れない。
- [ ] 各記録の内容・判定・出典を原資料と照合した。
- [ ] 出典リンクが対象の発言を指し、AIの推測URLがない。
- [ ] 未確認の記録を公開せず、AIだけの確認に確認済み表示を付けていない。
- [ ] 当時の対応状況と、後年の市の動きを混同していない。
- [ ] 公開後のURLを開き、表示と検索を確かめた。

### 4. ここまでできたら次へ

**確認済みの記録を探して読め、公開先でも動作を確認できたら、ステップ8へ進みます。** 検索ページ作成で止まった場合は、ステップ5までのデータを保存し、最後の質問手順へ進みます。

<a id="step-8"></a>
## ステップ8：公開後に増やす・改善する

### 1. やること

今回は、次のうち1つだけ選びます。変更前のデータとページを手元に保存してから進めます。

- **過去分を追加する：** ステップ1〜5で1件ずつ作ります。日付順に並べ直しても既存IDは変えません。
- **検索を改善する：** 表記揺れ・同義語・関連する呼称を試します。例えば、正式名称と普段の呼び名です。検索の対応語を増やすために、共通15分類の名称を変えたり増やしたりしません。
- **その後の市の動きを記録する：** 人が公開資料を読み、質問の対象に関係する事実を確認します。`follow_up` に、事実＋出典URL＋確認日を1行で記録します。これは暫定・将来変換対象です。
- **デザインを改善する：** 文字の大きさ・余白などを1か所変え、スマートフォンでも読めるか確認します。

`follow_up` は[暫定仕様のメモの書き方](データの形_暫定版.md#その後の市の動きの暫定メモ)に従います。

```text
（確認した事実）。（出典：URL、YYYY年MM月DD日確認）
```

最初の括弧は説明用です。実際には確認した事実の文を書きます。確認日は、人が資料の内容を確認した日です。未調査・未確認・出典不足なら `null`。これは「動きがない」の意味ではありません。

提案との因果を主張せず、「成果」「実現させた」と書きません。後年の情報で `result_level` を上書きしません。当時の読み違いを直す場合は、後年の進展と区別し、訂正の根拠を残します。

```text
元データを残し、既存ID・slug・項目名・共通15分類を維持してください。
追加データはstarter-0.1に従い、原文確認は私が行います。
follow_upを扱う場合は、私が確認した事実・出典URL・確認日だけを1行にしてください。
足りなければnull。因果を主張せず、後年の情報でresult_levelを変えないでください。
必要な情報が足りない場合は質問し、次の作業を1つだけ示してください。
```

### 3. 自分で確認すること

- [ ] `follow_up` は、人が確認した事実・出典URL・確認日付き。因果を主張していない。
- [ ] 公開後に、自分で変更の反映を確認した。
